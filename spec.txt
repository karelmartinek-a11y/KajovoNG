FORENZNÍ PODKLAD PRO ODBORNÉ POSOUZENÍ
Limity kontextu a výstupu při generování souborů v OpenAI Batch API

ÚČEL A ROZSAH

Dokument popisuje konkrétní neúspěšné dávkové generování projektu KájovoCML,
odděluje doložená zjištění od neověřených hypotéz a předkládá návrh změny
orchestrace pro odborné posouzení. Není implementační specifikací schválenou
k realizaci ani potvrzením funkčnosti výsledného projektu.

Uživatel požaduje, aby přípravné fáze vytvořily natolik přesné a provázané
kontrakty, že generování jednotlivého souboru nebude vyžadovat celé původní
zadání, celý plán a celou strukturu projektu. Zmenšení kontextu nesmí znamenat
ztrátu požadavků, rozhraní nebo kvality implementace.

Při sepisování dokumentu nebylo spuštěno nové placené generování. Dokument
neobsahuje API klíče ani plný obsah provozních požadavků. Odkazuje na lokální
důkazy, které nejsou součástí Git repozitáře. Samotné zaslání tohoto dokumentu
specialistovi tedy nepředává celou důkazní sadu.

3. PŘESNÁ PODOBA SOUBOROVÉHO POŽADAVKU

Každý požadavek na /v1/responses obsahoval:
- instructions: společné instrukce kvality a instrukce fáze A3;
- input: jednu uživatelskou zprávu se dvěma položkami:
  1) input_file s file_id již nahraného SSOT_CURRENT.txt;
  2) input_text obsahující JSON {specification, file};
- specification.requirements: celé původní A0R;
- specification.plan: celý A1;
- specification.structure: celou finální strukturu A2Q;
- specification.maximum_quality: true;
- specification.source: pokyn chápat přílohu jako normativní autoritu;
- file: kontrakt právě jednoho cílového souboru;
- text.format: strict JSON schema A3_FILE s pevnou cílovou cestou;
- reasoning.effort: xhigh;
- max_output_tokens: 16384;
- store: false;
- žádné tools ani previous_response_id.

Struktura byla bezeztrátově převedena na tabulku file_columns + files,
aby se neopakovaly názvy klíčů. Rekonstrukce tabulky byla kontrolována proti
původní struktuře. Šlo o úsporu zápisu, nikoli o výběr relevantního kontextu.

Příloha byla nahrána jednou jako soubor purpose=user_data. Každý požadavek
na ni odkazoval prostřednictvím input_file. To neznamená jednou zpracovaný
kontext pro celou dávku. Jednotlivé úlohy byly samostatné a každá měla tento
obsah ve svém vstupu. Vykázaný cached_tokens pro dokončenou dávku luny je 0.

Požadavky měly obsahovat celý cílový soubor v jedné odpovědi:
{
  "contract": "A3_FILE",
  "path": "<pevně určená relativní cesta>",
  "content": "<celý obsah souboru>",
  "chunking": {
    "chunk_index": 0,
    "chunk_count": 1,
    "has_more": false,
    "next_chunk_index": null
  }
}

Případné pokračování bylo tímto schématem zakázáno. Generování nemělo
nástroje pro spuštění testů, kompilaci ani práci s výsledky souběžných úloh.
Požadavek na testovací soubor znamenal napsání testu, nikoli jeho provedení.

5. CO JE PROKÁZÁNO A CO ZŮSTÁVÁ NEVYSVĚTLENO

Prokázáno:
- Počítadlo client.responses.input_tokens.count bylo voláno pro každý
  finální request; používalo pole model, instructions, input, text, reasoning.
- V uloženém token-count souboru existuje záznam pod digestem každého přesně
  odeslaného body. Per-model JSONL odpovídají příslušným řádkům společného JSONL.
  Nebyla zjištěna záměna spočítaného a odeslaného obsahu.
- Dokumentace mini uvádí okno 400 000 tokenů. Tvrzení „mini má určitě menší
  dokumentované okno“ proto není doloženým vysvětlením tohoto incidentu.
- API mini přesto všechny vstupy odmítlo a neposkytlo skutečný počet tokenů,
  použitý interní limit ani další rozklad chyby.
- U luny je příčinou nedokončení vyčerpání max_output_tokens. Limit zahrnuje
  uvažování i viditelnou odpověď; platné schéma samo nezaručuje dokončení.
- Stav Batch completed a HTTP 200 nestačí k prohlášení souboru za hotový.

Neověřené hypotézy pro mini, nikoli závěry:
- Rozdíl započítání nebo rozbalení input_file mezi count endpointem a Batch.
- Další interní režie nebo efektivní rezerva, kterou count nereprezentuje.
- Nesoulad modelového aliasu/snapshotu nebo konfigurace zpracovávající služby.
- Jiný problém implementace API při zpracování této konkrétní velikosti vstupu.

Bez informace od poskytovatele nebo řízeného reprodukčního experimentu nelze
mezi hypotézami rozhodnout. Snížení velikosti vstupu by mohlo problém obejít,
ale samo by nevysvětlilo tento rozpor. Placené pokusy nebyly při posouzení
odeslány. Případný experiment má vyžadovat schválený rozpočet a předem určené
varianty, nikoli opakované posílání celé dávky naslepo.

6. ODPOVĚDNOST ZA PŘÍPRAVU A ARCHITEKTONICKÉ NEDOSTATKY

Konkrétní chybné volby při ruční obnově:
- Plné zadání bylo přiloženo ke každému souboru současně s kompletními
  requirements, plánem a strukturou; neexistoval výběr implementačního kontextu.
- Kontrola mini pracovala téměř na hraně okna bez empiricky ověřené rezervy.
- Vysoké reasoning bylo plošně zkombinováno s malým výstupním limitem.
- Jedna kompletní odpověď byla povinná i tam, kde nebylo ověřeno, že se vejde.
- Modely byly rozděleny podle přípon, bez doložené validace vhodnosti pro úlohy.
- Celá sada byla odeslána před ověřením reprezentativních skutečných výstupů.

Počítadlo tokenů a cenová rezervace nebyly zárukou přijetí ani dokončení.
Původní projekce přibližně 58 USD byla rozpočtem jednoho průchodu, nikoli
důkazem dokončitelnosti včetně opakování a integračních oprav.

V běžném zdrojovém kódu:
- kajovo/core/generate_batch.py::build_manifest vytváří snapshot obsahující
  prompt, plan, structure, requirements a maximum_quality a vkládá jej do
  context.specification pro každý soubor.
- encode_requests ověřuje integritu celého snapshotu. Nestačí tedy odstranit
  prompt z jednoho místa: změna potřebuje nový kontrakt manifestu a validace.
- kajovo/core/delivery_preparation.py a requirements.py kontrolují schémata,
  pokrytí requirements a deklarované vazby architektury a souborů.
- Existence requirement_ids, provides, requires a dependencies sama o sobě
  nedokazuje, že příjemce zná přesné signatury, datové typy, chybovou sémantiku
  a všechny behaviorální povinnosti nutné pro implementaci.
- HTTP/API úspěch musí být oddělen od platného artefaktu a od jeho funkčnosti.

7. NÁVRH CÍLOVÉ ORCHESTRACE K POSOUZENÍ

A0/A0R — příjem a výklad zdroje:
Uchovat úplné zadání jako kanonický lokální artefakt. Zavést stabilní odkazy
na sekce a přiřazení requirements ke zdroji. Dlouhý zdroj je vstupem analýzy,
nemá být automatickou přílohou každého následného souborového požadavku.

A1 — architektura a společné kontrakty:
Definovat hranice komponent, datový model, vlastnictví stavu, sdílené typy,
rozhraní, verze závislostí, chybové konvence a globální invarianty. Každé
rozhraní má jednoznačného vlastníka a verzovaný kontrakt. Vyřešit rozpory
mezi požadavky ještě před rozdělením práce po souborech.

A2 — implementační kontrakt každého souboru:
Připravit skutečně použitelný pracovní balíček. Navržené položky:
- identita: path, role, language, action, verze kontraktu;
- přesné odpovědnosti a jejich hranice;
- relevantní requirements v plném potřebném znění, nejen jejich ID;
- veřejné exporty/signatury, typy, serializace, jednotky, nullability;
- stavové přechody, validace, autorizace, chyby, retry/idempotence, transakce,
  souběh a persistence, pokud je daný soubor realizuje;
- importy a přesné kontrakty použitých rozhraní včetně verzí;
- relevantní společné invarianty a bezpečnostní povinnosti;
- konkrétní akceptační kritéria a relevantní testovací scénáře;
- požadované prostředí, konvence frameworku a pravidla náhrad v testech;
- zdrojové odkazy s hashi pro audit;
- explicitní předpoklady a seznam nevyřešených závislostí.

Položky nemají být slepě opakovaným obřím checklistem. Musí být relevantní
pro odpovědnost souboru. Malý konfigurační soubor má jiný kontrakt než runtime
modul s transakcemi. Specifikace chování má být určitá, ale nemusí předepisovat
každý interní implementační detail.

A2Q — kontrola dostatečnosti a konzistence:
Kontrolovat nejen pokrytí ID, ale i shodu poskytovatelů a odběratelů rozhraní,
úplnost datových typů a chybové sémantiky, konflikty invariantů a nezajištěné
akceptační podmínky. Nevyřešená otázka kritická pro implementaci blokuje A3
konkrétního souboru a vrací se k opravě příslušného kontraktu.
Sémantickou dostatečnost nelze formálně zaručit pouhým JSON schématem ani
jedním modelovým posudkem; musí se doplnit integračními kontrolami a testy.

A3 — generování z omezeného, úplného pracovního kontextu:
Deterministický sestavovač z kanonických kontraktů vytvoří file_context:
  contract_version, source_snapshot_hash, target_file_contract,
  applicable_invariants, dependency_contracts, acceptance_criteria,
  relevant_source_excerpts, verified_dependency_artifacts.

Celé zadání, celý plán ani kontrakty nesouvisejících souborů se neposílají
automaticky. Přesné výňatky zdroje doplní pouze informaci, která není dostatečně
vyjádřena v kontraktech. Pokud je takových výňatků příliš mnoho, má se opravit
analytická příprava, nikoli bez kontroly připojit celý SSOT.

Závislosti se vybírají podle významu, nikoli slepým tranzitivním rozbalením
grafu, které by znovu přitáhlo celý projekt. Nutné tranzitivní typy a invarianty
se zahrnou; nesouvisející implementace se nepřidávají. Cykly se řeší společným
kontraktem rozhraní a koordinovanou skupinou, ne libovolným pořadím souborů.

Lokální auditní manifest může dál uchovávat kompletní zdroj a celkový plán.
API payload má obsahovat pouze konkrétní pracovní kontext. Hash manifestu
a hash skutečného payloadu mají odlišný význam a musí být evidovány odděleně.

Příklad tests/generation/workflow.test.ts:
Potřebuje testované chování, přesné importy/signatury workflow, význam stavů
a chyb, testovací framework, fixture kontrakty, pravidla mockování a očekávané
výsledky scénářů. Detail nesouvisejícího UI nebo jiného subsystému se nepřidá,
pokud není skutečnou závislostí testovaného chování.

8. PLÁNOVÁNÍ DÁVEK A OŠETŘENÍ LIMITŮ

- Generovat po skupinách závislostí: stabilní kontrakty/typy, poskytovatelé,
  konzumenti, navazující testy a integrace. Uvnitř skupiny dávkovat nezávislé
  úlohy. Batch sám nezajišťuje závislost výsledku jedné úlohy na druhé.
- Ověřené exporty nebo nutné části již vytvořeného kódu přidávat navazujícím
  úlohám s hashem a verzí. Změna kontraktu musí invalidovat dotčené konzumenty.
- Tokeny počítat nad přesným finálním payloadem a uložit model/snapshot,
  hash payloadu, souborové hashe, výsledek count, max_output_tokens a rezervu.
- Podmínka přijetí: input_count + output_budget + safety_margin <= model_limit.
  Velikost rezervy je návrhový parametr k ověření, nikoli zjištěná konstanta API.
- Zavést samostatný rozpočet kontextu na úlohu; překročení vrací přípravu
  k úpravě. Nezapínat tiché ořezání vstupu, které by odstranilo povinnosti.
- Limit výstupu i reasoning volit podle úlohy. Rozsah 32–64 tisíc výstupních
  tokenů je pouze kandidát pro vybrané složité úlohy, nikoli univerzální řešení.
  Snížení reasoning může pomoci ceně a délce, ale vyžaduje ověření kvality.
- Pokud celý soubor nevychází, nespojovat kusy neúplného JSON naslepo.
  Posoudit buď menší odpovědnost souboru, nebo explicitní verzovaný protokol
  pokračování. Ten by vyžadoval kontrolu pořadí, integrity a úplnosti; nejde
  o automatickou změnu stávajícího chunking kontraktu.
- Před velkou další skupinou ověřit malou skupinu skutečných pracovních úloh
  a její výstupy použít. Neposílat placené bezúčelné kompatibilitní sondy.
  Projektový SSOT nyní zakazuje samostatný placený preflight; případná změna
  této politiky musí být výslovně posouzena. V tomto incidentu uživatel navíc
  požaduje před dalším odesláním nejprve vysvětlení a projednání postupu.

9. IMPORT, OBNOVA A OCHRANA INVESTOVANÉ PRÁCE

Úspěch má více úrovní: přijatý požadavek -> terminální Response -> platný JSON
správného kontraktu -> bezpečný soubor -> obsahově správná implementace ->
úspěšná integrace. completed na úrovni Batch je pouze terminální stav dávky.

Import musí pro každý custom_id zkontrolovat HTTP status, error, body.status,
incomplete_details, odmítnutí odpovědi, schéma, cestu, neprázdný očekávaný obsah,
akci a případný protokol chunků. Následně bezpečný zápis, syntaxi a vhodné
obsahové kontroly. Žádný soubor neoznačit jako dokončený pouze podle počítadla
completed z Batch API.

Obnova má vycházet z lokální evidence výsledků s hashi, nikoli z opakování
celé dávky. Neposílat znovu úspěšné a stále platné úlohy. completed_hashes
musí být ověřené proti aktuálním souborům i verzím jejich kontraktů.
Neznámý výsledek odeslání se nesmí automaticky zaměnit za neodeslaný požadavek.

Pro tento běh: zachovat A0R/A1, finální přípravu, 38 dokončených odpovědí,
33 neúplných odpovědí a chybové záznamy mini. Obsah 38 výsledků nejprve
ověřit; nezaručovat jejich použitelnost před kontrolou. Neúplné texty mohou
pomoci opravě, ale nesmí být vydávány za hotové soubory. Zbývá 261 úloh
bez dokončené odpovědi, případně další opravy zjištěné obsahovou validací.
